# Beeline Route Planner

Демонстрационный диспетчерский планировщик выездных бригад. Он распределяет заявки между исполнителями и строит порядок посещений с учётом временных окон, квалификации, транспорта, оборудования, смен и принадлежности к участку. Для аварий поддерживается перепланирование в течение дня с сохранением исходного и дочернего планов.

## Возможности

- **Baseline** — заявки в исходном порядке назначаются первой подходящей бригаде.
- **Optimized** — C++ solver строит и улучшает маршруты; перед выдачей Python verifier независимо проверяет решение.
- Диспетчерский интерфейс с KPI, режимами Baseline/Optimized, интерактивной Leaflet-картой, фильтрацией по участкам, списками бригад и заявок.
- Объяснение назначения и отклонённых альтернатив через API.
- События: изменение статуса/отмена заявки, новая аварийная заявка, недоступность бригады; replanning создаёт отдельный child plan, diff и историю.
- SQLite persistence: планы, снимки входных данных, метрики, конфигурация solver, события и parent/child-связи.

## Архитектура

- `backend/` — FastAPI, Pydantic, SQLAlchemy/SQLite, доменная модель, расписание и ограничения, импорт данных, replanning и explainability.
- `cpp_solver/` — C++20 оптимизационное ядро, подключённое к Python через pybind11.
- `backend/app/constraints/verifier.py` — независимая финальная проверка назначений, расписаний и метрик. Результат solver не должен считаться подтверждённым без успешной проверки.
- `frontend/` — React, TypeScript и Vite. Карта использует Leaflet и OpenStreetMap с атрибуцией; координаты и линии демонстрационные, дорожная навигация не рассчитывается.
- SQLite — локальное хранилище планов и событий; по умолчанию файл `beeline.db` в корне проекта.

## Бизнес-правила

- `section_id` — участок и жёсткая граница: заявка назначается только бригаде того же участка. `region_id` поддерживается как legacy-поле/fallback; если оба значения заданы, используется `section_id`. Пустой участок совпадает только с пустым.
- `district` — информационное поле. Разные районы одного участка не запрещают назначение.
- Необходимые skills, transport и equipment — жёсткие ограничения. `LOCAL` — skill, BK/HD — источник классификации, не тип работы.
- Длительность на объекте нормализуется по справочнику: CONNECTION 70, EMERGENCY 80, ADD_ON 20, REPAIR 30 минут. Travel time рассчитывается отдельно.
- Время заявки должно соответствовать её release time и окну; расписание должно укладываться в смену бригады. `available=false` исключает бригаду, `available_from` и переданная текущая позиция учитываются при планировании.
- Статусы относятся к заявкам, а не автоматически ко всей бригаде. `COMPLETED`, `IN_PROGRESS` и `ON_THE_WAY` фиксируют заявку за прежней бригадой/порядком; текущая работа `IN_PROGRESS` не вытесняется аварией. Будущие незафиксированные заявки могут перепланироваться. `CANCELLED` исключается из активного маршрута.
- Новая авария получает `release_time`, равный времени события, и не может начать обслуживание раньше этого момента. При событии недоступности бригады её будущая работа пересматривается.
- Фактическое выполнение не выводится из прошедшего планового времени. Диспетчер должен передавать реальные status events (например, `COMPLETED` или `IN_PROGRESS`) до перепланирования; расписание само по себе не подтверждает выполнение.
- Приоритеты: EMERGENCY выше CONNECTION, затем REPAIR/ADD_ON. Сравнение решений лексикографическое: неназначенные заявки по приоритетным классам → число задействованных бригад → travel time → distance.

## Требования и сборка

Поддерживаемая среда сборки:

- Windows 10/11 и PowerShell;
- Python 3.12 или новее;
- Node.js `^20.19` или `>=22.12` и npm (ограничение Vite 8);
- g++ с поддержкой C++20 (команда `g++` должна быть в `PATH`) и MSYS2 UCRT64 runtime. Для текущего Windows setup runtime DLL ожидается в `C:\msys64\ucrt64\bin`.

Из корня репозитория:

```powershell
.\build.ps1
```

Скрипт создаёт `.venv`, устанавливает версии из `requirements.lock`, собирает pybind11 extension и production bundle frontend. C++ binary и `node_modules` не хранятся в репозитории.

## Запуск

```powershell
.\start.ps1
```

Если окружение или frontend build отсутствуют, launcher вызывает сборку. Он поднимает backend и production preview frontend, ждёт HTTP readiness и останавливает обе группы процессов через Ctrl+C.

- Frontend: <http://127.0.0.1:5173>
- Backend health: <http://127.0.0.1:8000/health>
- Swagger UI: <http://127.0.0.1:8000/docs>

Для отдельной локальной базы можно передать URL, например:

```powershell
.\start.ps1 -DatabaseUrl 'sqlite:///./beeline-demo.db'
```

## Быстрая демонстрация

1. Выбрать `demo_showcase` для показа навыков, разных транспортов и оборудования, временных окон и аварии; либо `combined` для масштабного результата.
2. Нажать **«Построить план»**, показать KPI, переключение Baseline/Optimized и статус проверки.
3. На карте выбрать участок, бригаду и заявку; открыть карточку и объяснение назначения/альтернатив.
4. Перед демонстрацией события обновить статусы уже завершённых и выполняемых заявок по факту — система намеренно не выводит `COMPLETED` из планового времени.
5. Открыть **«Событие в течение дня»**, указать время события и добавить аварию. Новая авария не прерывает `IN_PROGRESS`; она получает event-time release.
6. Показать новый дочерний план, diff, explanation и сохранённый исходный план. Полный командный сценарий приведён в [docs/DEMO_SCENARIO.md](docs/DEMO_SCENARIO.md).

## Результаты

Текущие проверенные значения относятся к одному API-прогону от 2026-09-29: seed `42`, запрошенный `time_limit_ms=3000`, default `SolverConfig`, `haversine_synthetic`, Python verifier включён. Все оптимизированные ответы в этом прогоне были полностью назначены и verified; в combined было 0 cross-section assignments. Полная таблица baseline/optimized, travel, distance, runtime и параметров — в [docs/BENCHMARKS.md](docs/BENCHMARKS.md).

**23 бригады для combined — результат конкретного запуска, а не доказательство глобального минимума.** Wall-clock ограничение может менять объём поиска и вторичные метрики. Результаты не являются гарантированными константами.

## Тесты

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -m pytest backend\tests cpp_solver\tests -q
Push-Location frontend
npm test -- --run
npm run build
Pop-Location
.\.venv\Scripts\python.exe scripts\full_flow.py
```

`full_flow.py` проверяет optimize → save → explanation → event → replan → restart → restore на тестовой базе. На момент текущего release audit backend/C++ suite имел 102 passing tests, frontend — 36; build и full flow прошли. См. ограничения проверки в [FINAL_RELEASE_AUDIT.md](FINAL_RELEASE_AUDIT.md).

## Ограничения

- Используется синтетическая Haversine-модель, а не дорожное routing; координаты демонстрационные, километры сравнительные.
- Leaflet загружает картографические тайлы OpenStreetMap с публичного сервера; для фоновой подложки нужен доступ к сети. Маршруты поверх карты остаются демонстрационными и не являются навигацией.
- Solver — bounded эвристический поиск. Глобальная математическая оптимальность не доказывается; 23-team результат не закреплён как target.
- Статусы и фактическая позиция бригады требуют входных событий/снимка. GPS-трекинга и календаря выходных нет.
- Emergency priority влияет на лексикографическое покрытие/назначение, но не гарантирует, что авария будет первой по времени среди всех допустимых будущих заявок.
- Runtime и вторичные показатели зависят от фактического поиска до wall-clock лимита.
