# Frontend Readiness Report

Дата проверки: 27.09.2026  
Проект: Beeline Route Planner v1.0.2 FINAL

## 1. Что изменено

- Основной экран собран как диспетчерский командный пункт: панель управления, текущий набор, состояние плана и verifier, KPI, сравнение решений, оперативная карта и панель ресурсов/заявок.
- Уплотнена desktop-компоновка. Карта и списки находятся рядом, список имеет собственную прокрутку, маршруты и остановки видны на схеме. Исправлена высота SVG-области: карта не схлопывается в пустой контейнер.
- KPI и сравнение отображают значения API. Во frontend не добавлен пересчёт качества/маршрутов и не зашиты benchmark-цифры.
- На карте сохранена схематическая подача: есть масштабирование, перетаскивание, слои маршрутов/аварий/неназначенных, офисы, номера остановок, направление маршрута и постоянная подпись о демонстрационных координатах.
- Список бригад показывает ID, участок, район, доступность, смену, транспорт, навыки, оборудование, число заявок, расстояние, travel time и времена arrival/start/finish.
- Добавлены вкладки «Бригады / Заявки / Неназначенные», поиск и отображающие фильтры заявок.
- Карточка заявки открывается поверх рабочей области и получает объяснение/ограничения/альтернативы из backend `/explanation`; предусмотрены loading, ошибка и повтор запроса.
- Сохранены переключение Baseline/Optimized, загрузка JSON, история дочернего плана и UI существующих сценариев события/replanning/diff. Во время расчёта отображаются этапы без выдуманного процента прогресса.

## 3. Используемые API

- `POST /api/optimize` — отдельные реальные ответы baseline и C++ optimized.
- `GET /api/plans/{plan_id}/requests/{request_id}/explanation` — объяснение заявки.
- `POST /api/plans/{plan_id}/events`, `POST /api/plans/{plan_id}/replan`, `GET /api/plans/{plan_id}/diff` — существующее перепланирование и diff.
- API сохранённых планов и история parent/child сохранены; контракты backend не менялись.

## 7. Demo flows

- В браузере выполнен реальный `zone_1`: baseline и optimized, переключение режима, отображение 66/66, 7 бригад, 417 минут, 207,6 км и зелёного Python verifier; карточка заявки получила backend explanation и hard-constraint checks.
- `scripts/full_flow.py`: optimize → save → explanation → CANCELLED event → replan → diff → новый app/SQLite restore; parent и child прошли verifier, restart/restore успешен.
- Отдельно проверен API-сценарий `IN_PROGRESS + NEW_EMERGENCY`: фиксированная заявка 9001 сохранила бригаду 9101 и осталась перед новой аварией 9006; дочерний план verified, diff содержит новую заявку и изменённый маршрут.

## 8. Ограничения и незакрытое

- Backend не поддерживает полноценное событие `TEAM_UNAVAILABLE`. Поэтому UI не имитирует недоступность бригады и не показывает фиктивную форму. Для полного этого сценария понадобится отдельное backend event/API изменение.
- Районы/координаты демонстрационные; карта намеренно схематическая, а линии не заявлены как дорожная навигация.
- Текущий verified-план подтверждается backend Python verifier; frontend не пытается выполнять эту проверку повторно.

## 9. Подтверждение границ изменений

В рамках этой работы не изменялись backend, API-контракты, datasets, C++ solver, objective, verifier и алгоритмы оптимизации. Изменения относятся к frontend и настоящему readiness-отчёту.
